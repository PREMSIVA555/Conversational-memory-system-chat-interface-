# T04.3 — Immutable policy ingestion and retrieval

T04.2 was approved by the actual user (“approved, proceed”) and completed in native Genesis. T04.3 implements SPEC08 / INV09. T04.4 explanations and P05+ remain queued/excluded. Human approval for T04.3 has not been given.

## What changed

An offline operator validates synthetic policy manifests with source SHA-256, unique immutable versions/sections, product/scope/locale, embedding model/dimensions and half-open UTC effective intervals. Counts, literal source spans, finite nonzero vectors and nonoverlapping versions of the same rule are checked before staging. Staging is idempotent and does not serve data. Activation atomically switches a complete immutable set using compare-and-swap against the previous set hash. A stale operator cannot overwrite a newer activation. Runtime and worker roles only read the catalog; ingestion is not an HTTP/customer/model tool.

Retrieval owns a read-only repeatable-read snapshot. It excludes ineligible chunks before exact cosine and PostgreSQL lexical ranking, then combines ranks using reciprocal-rank fusion (k=60). Exact search scans a bounded eligible corpus; it uses ordinary PostgreSQL storage and Python exact cosine, with no ANN, reranker, extension or new dependency. No query embedding is generated automatically: the caller must supply a vector from the configured model; an absent vector explicitly degrades the vector lane. Lexical SQL failures roll back to a savepoint, allowing eligible vector evidence to survive. Both lanes unavailable gives no evidence. No active/applicable set gives missing. Citation metadata includes immutable set, version, section, source hash and effective interval.

The corpus contains public synthetic policy text, so these tables have no customer payloads or tenant RLS. Existing customer tables retain their RLS and privileges. The retrieval library/CLI does not authorize customer banking operations. Customer chat integration and answer entailment are T04.4; retrieval explicitly returns answer_support=not_evaluated.

## How to check locally

Open PowerShell in `D:\Projects\Banking Assistant\banking-memory-agent`. This reads the existing local catalog as the restricted runtime role:

```powershell
.venv\Scripts\python.exe scripts/p043_policy.py query --product credit-card --scope retail --locale en-IN --question "annual fee" --at "2026-06-01T00:00:00Z" --embedding '[1,0,0]' --embedding-model fixture-v1 --limit 1
```

Expect status `ok`, both lanes `ok`, version `v1`, section `fee`, and the literal **synthetic** fee text. This is fixture data, not a real bank policy or generated financial advice.

- Change locale to `de-DE`: expect `missing` and an empty evidence list.
- Change time to `2028-01-01T00:00:00Z`: expect `missing`; the end boundary is exclusive.
- Remove `--embedding` and `--embedding-model`: expect `degraded`, vector unavailable and lexical ok. No silent live embedding call occurs.
- Omit `--at`: applicability is `current`; explicit times return `requested` applicability.

Do not look for a new policy answer in the browser yet. The existing accounts/cards/loan UI remains available at https://localhost:3443/. This task builds the policy evidence service. T04.4 will connect supported policy explanations to chat.

The offline ingestion commands are `validate MANIFEST`, `stage MANIFEST`, then `activate SET_HASH --expected PREVIOUS_HASH` (or `none` initially). A standalone manifest is required; the labeled evaluation file wraps a manifest plus queries. Commands use named policy DSN environment variables, or the existing private local config, and do not print DSNs. Avoid replacing the local demo set unless intentionally testing activation. Private test worlds are safer for mutation checks.
