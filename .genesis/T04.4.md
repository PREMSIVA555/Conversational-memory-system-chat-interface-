# T04.4 — Grounded policy explanations and domain regression

T04.3 was approved by the actual user (“approved and proceed”) and completed in native Genesis. T04.4 implements SPEC08 / SPEC09 and INV09 / INV10. P05+ is excluded. T04.4 human approval has not been given.

## What the conversation does

The LLM selects a registered read-only tool plan. It does not supply the displayed policy answer. Applicable policy evidence is read from the immutable catalog, and a small set of curated clause rules builds the explanation. This first set supports synthetic credit-card annual-fee and annual-spend fee-waiver clauses in INR. Unknown, conditional, conflicting or incomplete rule context yields a limitation. A policy cannot establish why a specific fee was charged, current customer spending or personal waiver eligibility.

The model cannot confer authority by adding customer identity, SQL, money-transfer or settings commands. Such plans are rejected by strict schemas. Tool/model attempts use the existing durable call and deadline budgets; retry/repair does not reset them. Worker reads recheck source erasure and session validity. Optional draft claims must match exact server evidence, and arbitrary draft prose is discarded even if it contains a real citation.

Required bounded context comes from the same eligible immutable snapshot independently of ranked hits. Unrecognized qualifications are retained and cause a limitation, rather than silently disappearing.

The policy service currently has no live embedding call. It explicitly records the vector lane as unavailable and uses lexical evidence only when it independently supports the complete material rule. This is a declared degraded mode, not a live semantic-model quality claim. Relevance and claim support have separate evidence. The exact vector/lexical baseline remains available in the T04.3 retrieval library and tests.

## How to check locally

The local API has been restarted with `BANK_POLICIES_ENABLED=true`; other runtime configuration is unchanged. The flag defaults false in source. Disabling it restores the registered bank-enquiry tools without policy answers. No schema migration or policy catalog rewrite was needed in this task.

Open https://localhost:3443/ and log in with an existing demo user. Create/select a conversation. Choose English response language for the checks below, or request en-IN explicitly when checking a translated reply. Try:

1. “Explain the credit card annual fee.” Expect the synthetic INR 100.00 rule and a citation to version v1 / section fee. The reply must say it does not establish a charged-fee cause or your eligibility.
2. “Explain the credit card fee waiver rule.” Expect annual spend INR 10000.00, with the same personal-eligibility limitation.
3. “Explain the credit card annual fee at 2026-06-01T00:00:00Z.” Expect applicability at that explicit timestamp.
4. “Explain the credit card annual fee de-DE.” Expect no applicable evidence, not an answer copied from another locale.
5. “Explain the credit card annual fee at 2028-01-01T00:00:00Z.” Expect no applicable rule after the end-exclusive interval.
6. Ask an existing account/card/loan question using its canonical reference. Exact banking facts should still come from owned fresh bank evidence.

Product must be explicit in the question. Retail is a declared scope default. Locale defaults to en-IN/hi-IN by response language; an explicitly requested other locale/scope or timestamp must be present in the question. No policy catalogue mutation is exposed to chat. Response-language templates preserve exact money and original citation/source metadata. Locale eligibility and response language are different settings.

These are synthetic demo policies, not real bank terms. Existing demo banking records are preserved. Live manual chat uses the configured LLM for planning; deterministic verification scripts replace only raw SDK outputs and make no paid calls.
