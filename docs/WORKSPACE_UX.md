## Data and execution

`api/workspace.py` exposes authenticated account/card/loan pages, automatic chat preparation and chat-message acceptance. `store/banking_workspace.py` uses the existing RLS providers. Each category loads independently with pages of20 and explicit unavailable states. Accounts/loans use stored names; only cards display actual last-four digits. UUIDs remain request references, not account numbers.

`resource_selection={kind,id,version}` is additive to the old account `selection` shape. Acceptance and execution verify ownership/version. Session-scoped server context retains an active product and at most20 latest result references for15minutes. Source sequence prevents late older results from replacing newer context. Clarifications publish a null marker rather than accidentally retaining an old category. Erasure removes dependent context; session rotation/logout clear mappings. A follow-up always re-reads bank data. Context never authorizes a foreign read or turns remembered amounts into current evidence.

Greetings, scope questions, policy reads and same-product details retain the latest displayed list; selecting a different product/category replaces it. Erasure dependency chains are also bounded at20 sources; after that conservative limit, select the product explicitly again. New migration0029 is checked out with LF via `.gitattributes` so new recorded bytes stay stable across Windows worktrees. During a bank DB outage, session revocation still succeeds: optional SQL cleanup is time-bounded/best-effort, and any remaining row is inaccessible under its revoked binding and logically expires. A later login cannot inherit it.

`graphs/workspace.py` handles bounded local intents and checked blocks, sharing `RunStore` deadlines, persisted reservations and source-fenced publication with the existing worker. Greetings, product discovery/taps and ordinary balance/history requests require no model. More unusual requests may use the existing minimized structured planner. Policy questions retain H01 locale/scope/time binding. Optional SDK errors preserve a checked answer; planning errors terminate safely instead of repeatedly reclaiming the lease.

The optional wording model selects audited conversational framing and an offered follow-up action. It receives the read operation/status/block kinds and available phrases/actions, not authority to rewrite balances or payment/policy conclusions. Invalid JSON, altered amounts, invented causes, eligibility promises or extra claims fail closed. **This is deliberately constrained framing, not free-form generated financial explanation.** The checked renderer remains the explanation authority. English/Hindi are supported; source names, ISO dates, currency codes and status tokens may remain literal. Some existing Settings labels remain English.

`WorkspaceChat.tsx` retains the original pending request ID across unknown acknowledgement/reload, checks session generation before rendering delayed replies, and merges source-backed turn/preference history. The visible chat uses durable status polling (1.8seconds), not unchecked financial token streaming. Existing SSE endpoints and durable replay remain available. Preferences use the existing entire-message typed grammar and durable receipts; Saved means persisted. Response-only commands retain the existing event-scoped preview semantics rather than becoming a permanent next-chat setting.

Chat scrolling follows reader intent: identical history refreshes never trigger a scroll. Changed content follows only while the reader is within64pixels of the bottom; scrolling up preserves the reading position. Sending an explicit new question resumes following the latest turn. `node scripts/ux_scroll_check.cjs` checks this in the actual UI with synthetic HTTP fixtures, including mobile and incoming/updated replies; it is separate from real OIDC/bank-data browser evidence.

## Verification and honest limits

### T05.3 reconciliation and owned case continuity (approved2026-10-25)

Additive0032 installs durable submission intents, current status timestamps and an immutable status-event trail. Enable `BANK_SUPPORT_CONTINUITY_ENABLED=true` only after `python scripts/p053_upgrade.py --recorded-migrations <original-checkout>/store/banking_migrations`. The guarded installer checks Docker identity, existing migration hashes and unchanged financial-resource hashes; no ordinary reset. This flag defaults false and preserves the approved T05.2 compatibility behavior when disabled. P05 remains partial and T05.4 stays queued.

The browser first performs authenticated GET `/support/proposals/{id}/outcome`. Before acceptance it receives a stable prepared UUID derived from the immutable preview ID/hash. Explicit confirmation first reserves the original accepted key in its own transaction, then runs the existing T05.2 five-record atomic effect transaction. An accepted intent alone is not a successful case. Failed effects can leave only that intent; repeated GET outcome or CSRF-protected POST `/support/proposals/{id}/reconcile` never creates effects. An explicit retry uses the original key/version/hash. Reload and missing browser operation storage recover the same prepared identity before acceptance or the durable original identity after acceptance. Existing committed0031 operations are backfilled; an unaccepted old random-key attempt cannot be recovered server-side if its only browser identity was lost before the upgrade.

The UI freezes uncertain submissions, requires a successful lookup before enabling retry, and labels a known creation receipt separately from checked current case status. An optional failed current-status read preserves a known successful receipt. After24hours the replay receipt may be absent while durable case identity still prevents duplicates. Pending previews can be cancelled/replaced under the existing exact-binding rules; replaced previews have different IDs, so old attempts cannot authorize the new draft.

Authenticated GET `/support/cases` supports owned keyset paging (limit1–20), and `/support/cases/{id}` returns current metadata/status timestamps. Later logins of the same customer can read these records; old preview/operation session authorization remains denied. No issue payload or operation/session credentials appear in the case list/detail. Source erasure scrubs case issue text and blocks source reconciliation; minimal owned case metadata remains readable. Logout clears UI/storage and delayed response guards prevent old-session restoration.

Only a migrator fixture function can advance created→in_review→resolved, with an immutable status event. No HTTP status writer, runtime grant or model tool exists. The ordinary review demo is not advanced by tests. This work adds neither external delivery nor financial mutations. Local paid transport remains blocked. Reviewable manual scenarios P05-M13–M18 are **Not run** until a human actually executes them; current machine receipts and limits are in `.genesis/T05.3.md`.

### T05.2 local confirmation (approved2026-10-25)

`BANK_SUPPORT_CONFIRM_ENABLED` defaults false. Enable it only after additive0031 is installed with `python scripts/p052_upgrade.py --recorded-migrations <original-checkout>/store/banking_migrations`; the installer validates actual Docker identity, existing hashes and unchanged financial resources. Earlier migration files remain immutable. The authenticated capabilities route enables a separate **Submit support request** button only for the saved exact description; unsaved edits must first be saved. No model tool can confirm.

Confirmation uses a canonical operation UUID plus exact preview version/hash. The trusted transaction reauthorizes the current session/product, serializes with source erasure/edit, and creates case, mandatory business audit, immutable creation receipt and local outbox before consuming the proposal. Runtime cannot directly write those new tables. An audit/receipt/outbox/commit failure rolls back everything. Optional telemetry stays on its existing bounded exporter path. No external support delivery or worker/status-advance capability is added.

Same key/body returns the same creation receipt within24hours. Same key with changed body conflicts. A consumed preview with a new key, or an expired receipt, returns409 plus an authorized existing-case reference. Durable proposal/customer-source uniqueness outlives receipt replay retention. Replay rechecks current authentication, ownership, source/session and resource access; it never authorizes another login. Receipts describe creation, not current support status. Source erasure scrubs the case issue payload and removes preview text; minimal case uniqueness/audit/receipt/outbox metadata remains without issue text. This retention choice must remain visible to future erasure/continuity work.

The browser retains its original confirmation key under the current login in session storage, freezes editing after uncertain submission, and offers **Check original submission** using exactly that request. It retains successful keys for same-login reload recovery. It never automatically mints a new key to resolve uncertainty. Disabled browser storage limits refresh recovery; full operation reconciliation and current owned case status across later logins remain T05.3. The browser test intentionally drops a real post-commit acknowledgement; SQL fault tests stay in private guarded worlds. Live provider transport remains blocked. Human scenarios P05-M09–M12 remain Not run until actually observed.

### T05.1 workspace integration (approved2026-10-25; baseline behavior)

Completed banking answers offer **Get help with this**. The support editor selects the source answer's owned product, or lets the customer choose General/account/card/loan and a friendly owned product from paginated APIs. No account UUID entry is required. General has no resource. The server rechecks ownership on every preview read/write; the displayed friendly name is outside the immutable hashed payload.

Save persists an exact normalized description as a pending immutable preview. Editing cancels the old version and inserts a new one atomically. Cancel and server-clock expiry disable editing. Refresh restores persisted state; an uncertain mutation acknowledgement blocks another write until refresh. Delayed responses cannot restore a previous login's editor. Preview polling occurs only while its editor is open and does not continuously scroll the chat. No LLM writes the issue text. In the T05.1-only baseline there is no submit-case button and the dedicated confirm endpoint returns503; the separately enabled T05.2 behavior is described above.
